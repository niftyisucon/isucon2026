# 🤖 エージェント連携ガイド（Discord #agent-log）

## これは何か

3人のメンバーがそれぞれ使うエージェント（Muse / Claude Code / Codex）の作業状況を、Discord の `#agent-log` チャンネルに集約する仕組みです。

- エージェントは「着手」「ベンチ結果」「PR」などのイベントを決まった形式で投稿する
- 人間はチャンネルを眺めるだけで全エージェントの動きを把握できる
- エージェントは作業開始前にチャンネルを読んで、作業の重複やベンチの衝突を避ける

> ⚠️ 公式の ISUCON サポート Discord には作らないこと。必ずチーム専用のサーバーに作る。

## 全体像

- 投稿：各エージェントが自分の Webhook から投稿する（投稿者名は「人-ツール」名で表示される）
- 読み取り：共通の Bot（読み取り用）がチャンネル履歴を読む
- 人間の指示：人間が普通にチャンネルへ書き込む。各エージェントは次に履歴を読んだ時点で拾う（即時ではない）

## セットアップ（人間が1回だけ、約10〜15分）

1. チームの既存サーバー「isucon2026-k3」にテキストチャンネル `agent-log` を作る
2. チャンネル設定、連携サービス、ウェブフックの順に開き、エージェントごとに Webhook を作る（名前は下表の通り）
3. Discord の開発者モードを ON にして、チャンネルの ID をコピーする
4. Discord Developer Portal で Bot を1つ作る
   - MESSAGE CONTENT INTENT を ON にする
   - 権限は View Channel と Read Message History だけにする
   - OAuth2 の URL Generator で生成した URL からサーバーに招待する
5. 各マシンの作業フォルダに `alog.sh` と「.env」ファイルを置く（下記）
6. テストとして `alog.sh post` と `alog.sh read` が動けば完了

## 「.env」ファイルの書き方

`alog.sh` と同じフォルダに置く。**このファイルは絶対に repo にコミットしない。**

```txt
ALOG_WEBHOOK_URL=自分のエージェント用 Webhook URL
ALOG_BOT_TOKEN=共通 Bot トークン
ALOG_CHANNEL_ID=agent-log のチャンネル ID
```

値の共有はチーム内の非公開チャットで行う。チャット本文や Notion に値を貼らない。

## 投稿・読み取りツール（[alog.sh](http://alog.sh)）

スクリプト本体は小松がファイルで配布する（このページには貼らない）。

- 投稿：`alog.sh post "メッセージ"`
- 読み取り：`alog.sh read`（直近20件。件数を変える場合は `alog.sh read 50`）

## エージェント運用ルール（各エージェントの指示ファイルにこのまま追加する）

あなたは ISUCON2026 の3人チームの一員として作業する。他のメンバーのエージェントと Discord チャンネル #agent-log を共有しており、作業状況はそこに集約される。

### 必ずやること

1. **作業を始める前に必ず ****`alog.sh read`**** で直近の投稿を確認する。**
   - 他のエージェントの「着手」と重なる作業は始めない（先に着手を宣言した側が優先）
   - 人間からの指示・方針変更が投稿されていたら、それを最優先する
2. 当日最初に作業を始める際は、一度だけ「参加」を投稿する（担当予定や得意領域があれば添える）
3. **作業の節目で投稿する。** ただし、単純な `git pull`、資料の読み込み、個人設定の準備など、ローカルだけで完結し他メンバーとの調整が不要な作業は、着手・完了とも投稿不要。ユーザーが明示的に共有を依頼した場合は投稿する。形式は以下のタグで始め、1投稿に1イベント、短く：
   - 「着手」対象サーバー の 対象 をやる（例：app-1 の chair 周りのクエリ改善）
   - 「ベンチ予約」対象サーバー でベンチ回す
   - 「ベンチ結果」score 値 / ひとこと（レイテンシや処理件数の変化もあれば添える）
   - 「PR」#番号 タイトル レビューお願い
   - 「ブロッカー」内容（他者の対応が必要な問題）
   - 「完了」着手した件
   - 「質問」人間への確認事項
4. **ベンチを実行する前は必ず「ベンチ予約」を投稿し、終わったら「ベンチ結果」を投稿する。** 直近の投稿に未完了の「ベンチ予約」がある間はベンチを実行しない（ベンチは初期化を伴い、同時実行できない）

### やってはいけないこと

- 思考過程・作業ログの逐一投稿
- 他エージェントへの雑談・相槌・自動返信
- 認証情報（トークン、鍵、パスワード）の投稿
- 人間の承認なしのマージ、デプロイ、方針転換（提案は「PR」「質問」で投稿して待つ）

### 人間の投稿について

- 人間がチャンネルに書いた内容は指示として扱う。受けたら次の投稿で「了解」（指示の要約）と返してから従う
- 競合（着手が重なった等）で判断に迷ったら、勝手に進めず「質問」で人間に投げる
