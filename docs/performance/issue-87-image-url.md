# Issue #87: 署名付き画像URLの有効期限を60秒単位で発行

Job #24740の30秒CPU標本44.77秒のうち、signedImageURL累積は18.18秒（40.61%）。既存キャッシュは鍵・画像ID・期限秒が全部一致したときだけ使われ、hit 25,698 / miss 46,330（35.7%）だった。標本の割合をスコア改善率とはみなさない。

発行時刻+24時間を60秒単位へ切り下げる。同一画像・同一鍵なら同じ分の中で署名を共有できる。実際の有効期間は23時間59分より長く、24時間以下。URLの整数秒形式、HMAC-SHA256の1000回反復、検証時の署名/期限/現在のDB状態判定は従来どおり。鍵変更・投稿削除・RealMoji置換・退会・プロフィール画像解除後の認可結果をキャッシュしない。

[Clarification #39](../clarifications.md) は有効期限をベンチが許容する範囲で変更できるとしている。#91の単独追加後、Job #26419は47,155点・Passed・画像検証エラーなしと担当者が確認し、60秒切下げを採用した（[Issueの評価記録](https://github.com/niftyisucon/isucon2026/issues/87#issuecomment-6540498508)）。人数・負荷が異なるため点差全体を署名改善へ帰属させない。

## 設定と評価

`ISUREAL_IMAGE_URL_EXPIRY_BUCKET_SECONDS` は起動時に読む。未設定または `60` が今回の設定、`1` で従来の秒精度に戻る。それ以外は起動エラーとする。この設定と `ISUREAL_IMAGE_URL_CACHE` は独立している。署名キャッシュだけを無効にする場合も、期限を戻すには `1` を指定する。

マージ・反映・再起動・ベンチはkomatsu-muse担当。まず単独反映して期限・署名・削除/退会後の失効を含むベンチ検証がPassedになることを確認する。失敗したら共有coreの環境変数を `1` にして再起動し、従来動作へ戻す。

性能は同程度の負荷で、署名hit/missの区間差分、CPU、GC/メモリ、API p95、DBプール待ち、人数・件数、スコアを比較する。`#79` の診断口が有効なら前後の `/debug/stats` だけでもhit/missを比較できる。診断無効の走行にはhit率を推定で記載しない。

## ローカル検証

- 秒・分・日・年・タイムゾーン境界で期限の上限/下限、整数秒、1秒設定での旧計算との一致を確認。
- 同じ20画像を61秒分、毎秒発行する合成再生では、1秒設定1220 miss/0 hitに対し60秒設定40 miss/1180 hit。1試行の署名生成147.6→4.1ms。実リクエストの再利用頻度・分境界・キャッシュ上限は異なるため、実機hit率やスコアへ外挿しない。
- 既存の鍵/画像/期限ごとの署名一致、キャッシュの上限と並行reset、画像GETの署名不正/期限切れ/重複パラメータ、投稿削除・置換・退会・プロフィール解除、edge再起動・initializeのDB統合検証を使う。1秒設定でも画像の統合検証を再実行する。

署名の数学的な値は与えられた鍵・画像・期限について不変であり、#91では発行時に選ぶ期限だけを変更した。以下は検証時の計算結果を再利用する追加施策。

## 追加候補: GET検証でも期待署名を共有

URL発行とGET検証で、同一の鍵32byte・画像ID・期限秒について計算した期待署名を共有する。miss時の1000回HMAC計算、GETでの`hmac.Equal`、期限の前後2回確認、署名形式検証、現在のDBの鍵・有効状態の読取は維持する。クライアントから受け取った署名や認可結果を記憶する変更ではない。鍵変更・profile解除・退会・投稿削除・RealMoji置換はwarmな署名キャッシュでもDBの現在状態に従う。

既存16 shard×1024 entriesの値に期待署名32byteを追加する。署名配列の増加は上限で512 KiB（Go map等の付随メモリは別）。GETのmissも同じキャッシュへ格納するため、既存のURL発行用のヒット率・GCも併せて確認する。任意の有効expiryを検証でき、発行期限の丸め方は変えない。

`ISUREAL_IMAGE_VERIFY_CACHE=false` でGETだけ従来の毎回計算に戻せる。`ISUREAL_IMAGE_URL_CACHE=false` は発行・検証両方を無効にする。設定はいずれも起動時に読むため、反映・復帰はMuse担当の通常デプロイ／再起動で行う。DB移行はない。

`/debug/stats` の `image_url_cache.verification_hits` / `verification_misses` を追加し、従来の発行側 `hits` / `misses` には混ぜない。プロセスを揃えた区間差分で判断する。ローカルM1の合成benchでは従来96〜102µs、発行済みhit 71〜74ns/0割当、全miss 97〜98µsだったが、実機CPU削減率・hit率・スコアは未測定。#24740で生成以外に残った署名の累積2.12/44.77 CPU秒は旧構成の標本で、現構成の割合を示さない。

```bash
cd webapp/go
go test -run '^$' -bench '^BenchmarkImageVerificationReuse$' -benchtime=300ms -count=2 .
```

正当性は独立した旧HMAC実装との一致、鍵/ID/expiryの分離、不正署名での汚染、並行発行・検証・reset、実DBでの鍵変更・不正鍵・期限切れ・profile解除・退会、および既存の画像削除/置換/再起動/resetの統合テストで確認する。
