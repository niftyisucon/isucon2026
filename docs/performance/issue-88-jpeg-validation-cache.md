# JPEG完全検証の結果を同じ入力に再利用する（#88）

Job #24740 の30秒pprofでは `decodeJPEG` が15.00 CPU秒、標本44.77 CPU秒の33.5%を占めた。
全ベンチやスコアの寄与率ではない。署名は #91、認証のDB待ちは #86 に別PRがあるため、
この変更は残るJPEG検証だけを扱う。pool上限・署名形式・有効期限・DB・保存方式は変更しない。

## 処理

`decodeJPEG` の結果が入力バイト列と寸法上限だけで決まることを使う。
投稿・プロフィール・RealMoji、海外edgeの事前検証で同じ関数を使う。

1. 2MiBを超える入力はキャッシュを使わず従来の `jpeg.Decode` と寸法検査へ進む。
2. SHA-256と寸法上限をキーに検索する。保持したバイト列と `bytes.Equal` でも一致した場合だけ成功結果を再利用する。
3. missは従来コードの完全デコード・寸法検査を実行する。不正JPEG・寸法超過は記憶しない。
4. 初回成功はdigestと上限だけ記録する。同じキーの再出現時も完全検証し、その成功後にバイト列をコピーして保持する。
   以後の完全一致だけがhitになる。初回からコピーすると全件miss時の割当が約50%増えたため、この方式にした。

保持上限は1プロセスあたり16 shard × 2MiB = **32MiBの画像本文**と少量のメタデータ。
各shardは本文64件・候補digest256件までで、満杯ならそのshardを消去する。
3リージョンを持つisu1では共用、海外edgeは各プロセスに独立して保持する。
冷えた状態で同じ画像の検証が同時に始まると、複数回デコードする場合がある。

認証・地域・閲覧権・所有者鍵・削除状態はキャッシュに入らない。
元のデコーダーを使うため、ヘッダーだけ通る破損JPEGを受理しない。
プロフィールの寸法超過と不正JPEGのabuse分類、edgeが偽の検証ヘッダーを捨てる順序も維持する。

initialize成功時、DB初期化世代の通知、edgeがinitialize成功を受けた時に候補・本文を消去する。
消去前に始まったデコードが後から戻っても、世代チェックによりキャッシュへ再挿入しない。
プロセス再起動時は空から始まり、画像本体の永続化には関与しない。

## ローカルでの比較

Apple M3 Pro / darwin arm64 / Go 1.27.3、固定乱数のYCbCr JPEGを使用。
同一画像のwarm hitと、JPEGコメントだけを毎回変更する全件missを別々に比較する。
warm hitの準備（2回の完全デコード）は計測外。実ベンチの画像再利用率は未計測。

```bash
cd webapp/go
go test -run '^$' -bench '^BenchmarkJPEGValidation$' -benchmem -benchtime=1s -count=3 ./...
```

| 合成入力 | 従来 | キャッシュ有効 | 割当 B/op（従来→有効） |
|---|---:|---:|---:|
| 512×512・warm hit | 4.69〜4.77ms | 73.5〜75.3µs | 407,088→0 |
| 512×512・全件miss | 4.64〜4.79ms | 4.72〜4.77ms | 407,088→約407,249 |
| 1024×1024・warm hit | 18.57〜18.65ms | 304〜308µs | 約1,586,753→0 |
| 1024×1024・全件miss | 18.66〜19.76ms | 18.91〜19.16ms | 約1,586,753→約1,586,868 |

入力本文は約205KiB/818KiB。warm hitの割当は0回、全件missの割当回数は従来と同じ5回/6回。
これはJPEG検証単体の合成比較で、APIやスコアが同じ比率で速くなるという意味ではない。
全件missではSHA-256と候補mapの追加コストがあり、3回の標本から厳密な遅延差は断定しない。
採用は実機でCPU・hit率・GC・p95・スコアを見て判断する。

## Museによる評価と戻し方

既定は有効。追加SQLやパッケージ導入は不要で、通常のコード反映で使える。
`ISUREAL_JPEG_VALIDATION_CACHE=false` を起動時に指定すると従来の完全デコード経路へ戻る。
比較時は署名・認証・DB pool等の設定を揃える。反映・再起動・ベンチはMuseが担当する。

既存のloopback診断を有効にしている場合、`/debug/stats` の `jpeg_validation_cache` から
`hits` / `misses` / `bypasses` / `entries` / `candidates` / `bytes` を採れる。
`bypasses` は2MiBを超えてキャッシュ対象外になった呼び出し数。画像・digest・IDは出力しない。
hit/miss等はinitializeでゼロに戻さない累積値なので、同じPIDの開始・終了差分を使う。
`tools/analyze-runtime-stats.py` はこの区間差分と、bypassも分母に含めたhit率、保持量の最大を出す。
旧バージョンのJSONLも解析できる。信頼済みedge proofでcoreが再検証を省く呼び出しは、このカウンターへ入らない。

対象Job・commit・PID・採取UTC・地域別人数を添えて、次を比較する。

- `decodeJPEG` のCPU、GC/割当、プロセスのメモリとJPEG cacheの保持量。
- hit/miss/bypassの区間差分、投稿・プロフィール・RealMojiのavg/p95、正当性とスコア。
- DBStatsのWaitCount/WaitDuration、InUse/Idle。CPUが空くことによる改善量は未測定で、pool待ち解消とは断定しない。

命中が少ない、大きな画像ばかりでbypassが多い、CPU/GC/p95が悪化する場合はfalseで比較する。
ローカルでは元デコーダーとの正常/破損/寸法境界/末尾追加/変異入力の一致、バイト照合・コピー保持、
容量制限、並行reset、認証・abuse・edge証明と初期化を検証する。
