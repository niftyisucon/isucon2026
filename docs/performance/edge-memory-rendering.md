# Memories の応答生成を海外エッジへ移す（#67 / #87）

## 対象と根拠

`GET /api/memories?month=...` と `GET /api/memories/:date` の成功応答について、画像URL署名とJSON生成を海外エッジへ移す。認証、リージョン制限、本人の投稿・現在有効な反応・コメントの取得は従来のcoreで行う。

旧Job #24740の30秒CPU標本では、`listMemories` の累積が11.67/44.77 CPU秒（26.1%）だった。#91の期限丸め・#107の検証キャッシュ導入前の値なので、現在の割合や改善見込みを示すものではない。新しいCPU標本は未取得。根拠データは `bench-data/job-24740/diagnostics/`。

## 通信と正当性

1. エッジは利用者が付けた内部ヘッダーを削除し、メソッド・URI・セッションに束縛したHMAC証明を付ける。
2. coreは従来の認証・リージョン制約を通した後、既存と同じ3 SQLでモデルを取得する（空ページは1 SQL）。本人の投稿、並び順、カーソル、50件上限、hasMoreを維持する。署名期限はcoreの時計と既存の丸め設定で決める。
3. coreはモデルをgob化し、共有EdgeKeyから用途別に導出した鍵とランダムnonceでAES-256-GCM暗号化する。既存のHTTP応答に暗号文を返すため、DB・HTTPとも往復回数は増えない。URI・セッションはAADにも含める。
4. エッジは暗号文を認証・復号し、従来の応答コンストラクタ、署名1000回計算、署名キャッシュで通常JSONへ変換する。投稿・反応・コメントのプロフィール画像も同様。URLの形式・期限・GET側の検証を変えない。

モデルには署名鍵と非公開のプロフィール画像IDが含まれるため、平文の内部JSONや外部応答として送らない。専用Content-Typeを受けたエッジは、証明不正・認証失敗・破損・8MiB超過時に汎用502とし、モデルを外へ転送しない。coreで8MiBを超える場合は通常のJSON生成へ戻すので、APIに新しい応答サイズ制限は設けない。モデル・認可結果はキャッシュせず、削除・置換・退会・鍵変更は毎回現在のDBを読む。キャッシュするのは既存の署名計算結果だけ。

署名期限はcoreで決めて全URLへ渡すため、海外側の時計差や設定差によって期限を延ばさない。日時・配列・JSONのエスケープ・Content-Typeを従来応答と比較する。公開先・固定リージョン・ルーター経由の通信・保存方式は変更しない。

## 有効化と切り戻し

`ISUREAL_EDGE_MEMORY_RENDERING=true` をcoreと対象海外エッジの両方へ設定したときだけ使用する。未設定・falseは通常経路。新エッジ＋旧coreは通常JSON、新core＋旧エッジは証明が付かず通常JSONとなる。先にコードを全台へ反映し、検証する場合にだけ有効化する。coreまたはエッジの設定をfalseにして再起動すれば通常経路へ戻る。DB変更やデータ移行はない。

マージ・反映・再起動・競技ベンチはkomatsu-muse担当。#114の地域別受付と独立であり、このPRはその設定を変更しない。終盤の採否は担当者に委ね、実機評価なしで改善を断定しない。

## ローカル測定

Apple M1、Go、30投稿×各10反応＋10コメント、300人の反応者とプロフィール画像を含む合成モデル、400ms×2回。SQL・ネットワーク時間を含まない応答生成部分のみ。warmは全署名が既存キャッシュへ入った状態、coldは各試行前にキャッシュを空にする。

| 処理 | 1回の時間 |
|---|---:|
| 従来のcore署名＋JSON（cold） | 61.84–62.24ms |
| 従来のcore署名＋JSON（warm） | 0.652–0.660ms |
| 新coreのgob＋暗号化 | 0.392–0.396ms |
| 新edgeの復号＋署名＋JSON（cold） | 62.61–63.04ms |
| 新edgeの復号＋署名＋JSON（warm） | 1.138–1.145ms |

coreのCPUを他のAPIに空ける施策であり、総CPUを同率削減する施策ではない。gobの復号・割当が増え、両端のGCと海外CPUも確認が必要。さらに、coreで署名を生成しなくなると#107の画像GET検証キャッシュを事前に温める効果が失われるため、画像GETのmissが増える可能性がある。海外が既にCPU律速なら悪化することもある。

再計測は `go test -run '^$' -bench 'BenchmarkEdgeMemory(Core|Receiving)Work' -benchmem -benchtime=400ms -count=2`。実機では同じアプリ版・設定でoff/onを比較し、core/edge CPU、Memoriesと画像GETのp95、署名生成/検証hit/miss、GC、DB待ち、地域別の採点件数、エラー、スコアを確認する。

## 検証

- DBありの旧API対エッジの月・日・空・カーソル・不正入力・認証失敗・地域変更・退会、削除/置換/プロフィール更新と50件境界を比較。
- coreの署名発行0回とSQL往復数3→3（空は1→1）を検証。
- リクエスト/セッション/鍵の違い、改ざん、切断、nonce差、過大モデル、外部からの偽ヘッダー、既定offを検証。
- core指定の期限と通常HMACの一致、既存の画像認可・失効・再起動・initialize回帰を含めて最新main（#114込み）でDBあり全体race 46.059s、vet、Linux amd64ビルドに成功。署名キャッシュOFF・期限1秒の設定でも期限/署名の回帰に成功。任意のトレース用DBテストは別環境変数で有効化するため、この検証には含めない。
- 競技ベンチ・実機再起動・実機性能比較は未実施。
