# 通知高速化と共有coreの混雑対策

Job #29880では通知開始が2.287秒から11msへ短くなった一方、asiaの成功投稿が101→584件へ増え、海外2地域は726→230件へ減った。core CPUは約40秒90%超で、投稿4.388秒のうち画像保存終了→BEGINに3.563秒の空白があった。SQL前の空白を全てpool待ちとは断定していない。Refs #63、#75、#109。

## 実装

- FoFフィードの候補・採点・詳細・所有者鍵は同じREPEATABLE READ snapshotで確定する。commitして接続を返した後に、最大50件の画像URL署名と応答を組み立てる。順序、ページ境界、認可条件は維持する。
- 共有coreの受付制御は `ISUREAL_CORE_ADMISSION=true` のときだけ有効。edgeと単一リージョンプロセスには適用しない。
- 認証、リクエストbodyの解析、DB取得より前に、リスナーの地域で通常APIの同時実行数を制限する。利用者のヘッダーや申告地域で枠を選ばない。待機中はDB接続を取得せず、429等の新しい拒否は追加しない。
- 既定の共有pool30では各地域9件。管理API・initializeは別の共有2枠、通知worker用に1接続の余地を残す。pool45/60では各14/19件。共有pool上限自体は変更しない。
- `ISUREAL_CORE_REGION_CONCURRENCY` で各地域の件数を1〜上記予算の範囲で下げられる。空いている他地域の枠は貸し出さないため、一地域だけの最大スループットは下がり得る。最適値・スコア効果は実機で比較する。
- SSEも認証とDB時計確認までは通常枠を使う。時計確認後、header flushや将来の通知を待つ前に返す。キャンセル・エラー・panicでも返し、二重返却はしない。

通常ハンドラーが同時に使うDB接続は既存実装では最大1本。受付制限はDB poolを物理分割するものでもCPU時間の予約でもない。アプリ外の接続、LISTENの専用接続、通知workerの負荷は別に考慮する。CPUそのものの不足は署名/JPEG等の削減・処理分担も必要で、接続上限の増加だけでは解けない。

### 地域別の枠数

共有coreで `ISUREAL_CORE_ADMISSION=true` のとき、`ISUREAL_CORE_REGION_LIMITS=asia:5,europe:11,america:11` を指定するとリスナー地域ごとに枠数を変えられる。全リスナー地域を重複・過不足なく指定し、各1以上、合計は共有DB接続上限−3以下とする。不正値や `ISUREAL_CORE_REGION_CONCURRENCY` との同時指定（両方が非空）は起動時panicになる。未設定・空文字なら従来の均等配分または既存の一律指定のまま。edge・単一地域プロセス・受付OFFでは適用しない。`/debug/stats` の `core_admission.<地域>.limit` で実効値を確認できる。

有効化用の任意テンプレートは `config/architecture/isu1/70-core-region-limits.conf`。自動反映されず、Museの通常デプロイで共有 `isureal-go` にだけ適用する。戻す場合はこのdrop-inと地域別設定を外し、以前の一律指定があれば復元して再起動する。受付自体を戻す場合は `ISUREAL_CORE_ADMISSION=false` にする。地域間で枠は貸し借りしないため、asiaの待ち時間増加や海外が空いている際の全体スループット低下があり得る。5/11/11のスコア効果は未検証で、CPU時間の確保も保証しない。利用者の振り分け・通信経路・認可・永続化は変えない。

## 通知の仕様修正との統合

PR #110（Issue #109）が、開始時点の対象者とランダム通知IDを窓1行に永続化する。地域往復の通知漏れ・誤配信、時刻境界、旧通知との混在、initialize、再起動後のID維持を守る部分であり、本変更はそのSQLやDDLを重複実装しない。

組み合わせる場合は #110 のDDL `webapp/sql/notification-snapshots.sql` と全読者更新が先。通知の新規書込は `ISUREAL_DERIVED_NOTIFICATIONS=true` の明示指定で初めて有効にする。旧方式への復帰後も保存済みsnapshotは修正版の読者で読める。未修正の #106 を受付制御だけ追加して有効化しない。

## 計測

既存のloopback診断待受 `/debug/stats` に `core_admission` を追加した。有効時のみ地域名と `control` ごとに以下を出す。PII、URL、token、SQL引数は含まない。

- `limit` / `in_use` / `waiting`: 上限と現在の実行・待機件数。
- `admitted` / `wait_count` / `canceled`: 累積の受付・待機発生・待機中または取得直後のキャンセル件数。
- `wait_nanoseconds`: 待機を終了した時に加算する累積時間。キャンセルした待機も含み、並列待ちの合計なので壁時計時間ではない。

APMには `core.admission.wait` を追加。受付待ちと既存pgx SQL span、DBStatsのWaitDurationを混同しない。共有30本に対して全地域の受付27件でも、長いSQL・取引保持の問題が消えるとは限らない。

## ローカル検証と実機比較

実DBテストでは、asiaを1枠で詰まらせ、同地域の12要求を待機させてもeurope・america・管理APIが同じDBで処理でき、待機中の要求がDB poolへ入らないことを確認する。SSEを2本開いたまま1枠設定で通常API・認証が動くこと、キャンセル・panicで枠が戻ることも確認する。

FoFは署名cacheのlockで整形だけを止め、1本しかないDB接続を別要求が取得・更新できることを検証する。整形中に投稿を削除しても確定済みsnapshotのページは維持し、次の取得では削除が見える。既存の600候補・ページング・権限の新旧比較も維持する。

実機の反映・ベンチはMuse担当。既定の受付制御OFFを基準に、まず受付ON＋通知旧方式、次にレビュー済み通知snapshotを組み合わせて比較する。Job・commit・設定・地域別人数を記録し、通知開始だけでなく投稿→フィードまでの完走、画像・閲覧数、地域別p95、core CPU、受付待ち、DBStats、メモリを評価する。競技ベンチと再起動試験はローカル検証で代替できない。

受付制御は `ISUREAL_CORE_ADMISSION=false` または未設定へ戻せる。DBスキーマや認可データを変えず、FoFの接続返却短縮はそのまま残せる。
