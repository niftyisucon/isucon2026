# 投稿期間の通知対象・IDを1行で保存する（#109）

## 変更

`ISUREAL_DERIVED_NOTIFICATIONS=true` の場合、期間開始の地域ロック下で対象ユーザーIDとランダムUUID v4通知IDを `posting_windows.notification_user_ids` / `notification_ids` に同じID順で保存する。対象者0人は空配列、従来の窓はNULL。既定・falseは従来のnotificationsへのINSERTである。

通知のcreated_atは従来から窓のstarts_atと同じ。読者は対象者配列を持つ全active窓と、配列を持たないactive窓のnotificationsを読み、created_at・通知ID順の先頭を返す。現在の所属地域で候補窓を限定しない。利用者の有効状態、購読地域との一致、接続時刻の厳密な `>`、initialize世代のチェックは維持する。配列は一度だけ展開して購読者とまとめて照合する。

期間開始時に地域を往復していたケースも旧方式と同じ結果になる。UUIDを読むたびに生成せず永続化するため、再起動や書込設定のfalseへの復帰でも同じ通知IDを返す。読者は書込設定にかかわらず両形式を扱う。既存notificationsの変換・削除は行わない。

## 反映・比較・復帰（komatsu-muse担当）

1. ベンチ外で `webapp/sql/notification-snapshots.sql` を適用する。小さいposting_windowsへのnullable列2個の追加のみ。既存データの書き換え・削除はしない。通常のarchitecture.sqlにも同じDDLを含む。
2. isu1/2/3の全プロセスを修正版に揃え、`ISUREAL_DERIVED_NOTIFICATIONS=false` を維持して再起動する。読者は起動時に列の存在を確認する。DDLより前に起動したプロセスは、DDL適用後に再起動する。
3. 比較する場合だけ全プロセスで明示的にtrueを設定し、ベンチ外で再起動する。列がないままtrueなら起動時エラーになり、現在の所属だけから導出する旧#106動作には戻らない。
4. 設定のfalseへの復帰は修正版のバイナリを維持したまま行う。開始済み配列を引き続き読める。古いバイナリへ戻す場合は配列形式を読めないため、ベンチ外で復帰しinitializeを経てから比較する。#106修正前の期間については開始時点の対象履歴がないため復元しない。
5. resetは追加後の窓を削除し、初期のNULL列・既存通知を保持する。独立した通知スナップショットテーブルや初期化専用の削除処理は不要。

## 検証

- 既存13シナリオを新旧両モードで確認。特に「開始時だけ別リージョン」「別リージョンの窓を挟む往復」は同じ期待値に修正した。
- 3地域が同時刻に開始したデータを使い、従来SQLが実際の通知行から返した結果と、2地域を配列へ移した混在データの結果を通知IDまで比較。重複購読、退会・不存在、since境界を含む。
- 登録・地域変更・退会・重複開始が実際にロック待機するテストを両方式で実施。待機前後の対象集合を確認する。
- 保存失敗時に窓の終了も含め全トランザクションが巻き戻ること、保存IDの一致、書込設定をfalseへ戻した後の読取、空配列、旧スキーマ、DDLの冪等性を確認する。
- LISTENの初回0行UPDATE・次回、未コミット/ロールバック、initialize世代、5000人の開始、全体race、vet、Linux amd64ビルドを確認する。

## 性能評価の範囲

本番の約185万通知行を参考に、ローカルPostgreSQL 16へ合成5000人・370終了窓・185万通知を作成。通常スキーマとインデックスを使い、同期書込は有効のまま比較した。ローカルの共有バッファは128MiBであり、実機のCPU・I/O・データ分布・同時負荷とは異なる。seed後にCHECKPOINTを完了させ、他のDBテストと重ねず計測した。

窓開始は、BEGIN・地域advisory lock・時刻取得・旧窓終了・新窓INSERT・通知の保存・COMMITまでを測った。9回交互に実行し、最初の2回を除く7回の値。APIの入力確認・競合SELECT・応答生成は含まない。試行で追加した通知行と窓を毎回削除し、同じ日付・異なる窓IDで比較した。

| 保存方式 | 中央値 | 最小〜最大 |
| --- | ---: | ---: |
| 旧方式の5000通知行 | 118.767ms | 90.923〜200.342ms |
| 対象ID・通知UUIDの2配列 | 11.746ms | 11.489〜12.090ms |

旧方式のばらつきが大きいため、この比を実機の改善率として扱わない。

500購読の読み取りは実装からSQLを取り出して `EXPLAIN (ANALYZE, BUFFERS)` で7回実行し、最初の2回を除いた5回の中央値。開始窓は全購読者を対象とし、複合インデックスを含む実スキーマを使った。読み取り各方式は順に測定した。

| 読み取り条件 | 中央値 |
| --- | ---: |
| 旧読者・旧形式データ | 2.460ms |
| 修正版読者・旧形式データのみ | 2.988ms |
| 修正版読者・配列形式のみ | 3.957ms |
| 配列形式に加えて旧形式のactive窓あり | 5.304ms |

最後の条件は、別地域にNULL配列のactive窓を1個追加し、旧通知索引の探索も必要になる条件。読み取りは旧方式より重くなる。大量INSERT・WAL・ロック保持の削減との交換なので、実機の通知SQL総時間も比較する。配列展開は購読者数ではなくactive窓の対象者総数に比例する。

最初の対象IDだけの試作は開始tx中央値87.15→5.24msだったが、完成版は通知UUIDの生成・永続化を含む。購読者ごとに `ANY` で配列を検索する試作は500購読で26.84ms（旧SQL2.45ms）へ悪化したため採用していない。完成版の読取では、配列形式の窓しか存在しない場合に旧通知索引の探索も省略する。旧形式・新形式が混在している期間の費用も評価する。

#29880では通知開始が数msになった一方、asiaの負荷増後に共有coreが約40秒CPU90%超となり海外の投稿・閲覧が減ったという観測がある。したがって、窓開始の短縮だけを採用基準にしない。単独比較でPassed・地域別人数/投稿/閲覧・CPU・DBプール待ち・通知SQL時間・スコアを見る。実機効果と採用は未確定。
