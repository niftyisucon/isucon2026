## 完成時の役割

| ホスト | 役割 |
| --- | --- |
| isu1 / asia1 | Go 1プロセスで asia :8080 / europe :8081 / america :8082。DBプール、画像キャッシュ、IP banキャッシュ、通知workerを共有。新規画像の本体を `/var/lib/isureal-images` に永続保存 |
| isu2 / europe1 | nginx → ローカルGo。JPEG検証、画像本体キャッシュ、SSE配信。その他のAPIと画像の有効性確認は isu1:8081 に転送 |

## 画像

- 新規投稿、プロフィール、RealMojiの画像を同じ保存処理へ統一しました。
- ファイルはSHA-256の内容アドレス。完全な書き込み、ファイルfsync、rename、ディレクトリfsyncの後にDB参照をコミットします。大きいファイルの保存はユーザー行ロックより前です。DBにはid・所有者・種別・作成時刻・storage_keyを残し、dataは空byteaにします。
- 初期画像は変更せず、storage_keyがNULLなら従来のDB blobを読みます。初期画像を一括エクスポートする必要はありません。
- 海外で初回取得した画像は画像IDをキーにキャッシュします。海外での `POST /api/posts` が201を返した場合も、JPEG検証済みのアップロード本体を応答の `imageUrl` に対応するIDでキャッシュします。応答本文は同じバイト列を返し、圧縮応答や解析できない応答では投入しません。ヒット時も署名・期限・現行の可視性SQLをasiaで毎回検証し、成功した場合だけ海外のバイト列を返します。有効性のキャッシュ、認可TTL、nginxの無条件な静的公開はありません。
- 画像の署名検証、削除・置換・退会に対する既存のSQL判定を保ちます。投稿の閲覧制限・友達・FoF・ブロックは従来APIの判定を通し、URL発行側を含めて緩和しません。画像削除の5秒猶予を他の状態変更に流用しません。
- メモリキャッシュの世代を管理し、initializeより前に開始した読み込みが後からキャッシュを復活させないようにしています。確認中にキャッシュが追い出された場合も、リクエスト開始時のバイト列を保持して内部204を公開しません。
- 再起動後は同じディレクトリから読みます。新規画像のファイルが失われた場合、DBの空byteaを200で返してはいけません。DB blobが残る画像だけはblobへフォールバックできます。ディスク正本はバックアップ対象です。
- ZIPエクスポートもstorage_keyを解決して元の画像バイト列を格納します。

ロールバックやinitializeでファイルを即削除すると、同じ内容を参照する別画像や並行トランザクションを壊すため、未参照ファイルは保持します。キャッシュはcoreが上限256MiB、`EdgeUpstream` 設定済みのエッジプロセスが上限1GiBで、超過時は従来どおり全消去します。永続ディスクの未参照ファイル回収は別途停止時間帯に行う設計です。既存データを自動削除するGCは追加していません。

投稿時のエッジキャッシュ投入は既定で有効です。エッジだけが起動時に読む `ISUREAL_EDGE_UPLOAD_IMAGE_CACHE=false` で、この投入だけを無効化できます（GETキャッシュとJPEG検証は維持）。投入には転送前に取得した世代を使い、initializeをまたいだ応答で古い画像を復活させません。RealMojiとプロフィールのアップロードは対象外です。切り戻しは担当者がエッジに同フラグを設定して再起動するか、本変更前のバイナリへ戻します。後者ではエッジ上限も256MiBへ戻ります。保存方式・DBスキーマの変更は不要です。

## 海外のJPEG検証

海外で元と同じjpeg.Decodeと寸法チェックを行い、画像バイト列のハッシュと寸法上限に対するHMACを付けます。asiaは共有鍵で検証できる場合だけ重複デコードを省略します。認証・権限・投稿条件の判定は全て従来のasia APIで行います。

公開リクエストに含まれる内部ヘッダーは海外で削除してから再計算します。無効画像は証明なしでasiaへ転送するため、認証エラーやabuse判定の順序を保ちます。証明は認証トークンでも閲覧許可でもありません。

## SSE

PR #56のバッチSQL・配信処理を再利用しました（元コミット aec6a0c）。接続ごとの時刻境界と本人の通知IDを保持し、1 workerが接続中の利用者をまとめて確認します。

architecture.sqlはnotifications、posting_windows、usersの変更にトランザクション内のpg_notifyを追加します。各プロセスはLISTENし、コミットされた変化で即座にバッチ確認します。ロールバック通知は配信されません。通知テーブルが永続の正本で、NOTIFYのpayloadをそのまま利用者に返しません。

通常時は5秒ごとのバッチ確認を取りこぼし対策として残し、LISTEN切断時は500msに戻します。トリガー未導入で起動した場合は再起動まで500msで動作し、チャネルだけ存在する状態で5秒待ちへ移りません。退会・リージョン変更は再確認して切断します。initializeはDBの世代を更新し、各バッチは接続時の世代と比較して古い購読だけを切断します。DB通知を取りこぼしても世代で判定し、遅延したreset通知で初期化後の新しい購読を誤切断しません。キャッシュはDB通知でもリセットします。

### SSEはDB直結を残す例外

通常APIのDB処理はasiaへ集約しますが、海外の `/api/notifications` はローカルGoが処理します。IP ban・セッション・リージョン確認、接続時刻と初期化世代の取得、通知バッチSQL、LISTENはisu2/isu3からisu4へ直接接続します。この通信にも既存ルーターの遅延・帯域制限がかかります。

海外の長時間接続と配信をasiaに集中させないための意図的な例外です。DBへの海外接続を全廃する構成ではありません。#56のバッチ化とNOTIFYにより確認回数を抑えますが、購読開始時や再確認時の海外DB往復は残ります。これもasiaへ転送する案との優劣は、実機で通知の遅延・asia CPU・DB接続数を比較して判断します。

## 追加レビューの検討（2026-10-31、実装2d245ef）

[akihisa-museの処理分担案](https://github.com/niftyisucon/isucon2026/pull/64#issuecomment-6539517558)と、同案を独立させた[Issue #67](https://github.com/niftyisucon/isucon2026/issues/67)を現在の処理順と照合しました。今回は説明の修正を行い、実行時の挙動は変更しません。

| 提案 | 今回の判断 | 理由 |
| --- | --- | --- |
| 期限切れURLをedgeで拒否 | 保留。asiaでの期限検証を維持 | asiaも期限切れは画像SQLの前に拒否済み。edge拒否で省けるのは主に海外HTTP往復と入口処理で、正常な画像取得の処理は減らない。時計差とIP banの優先順位も考慮が必要 |
| asiaの画像本体キャッシュを削除・初期画像専用に限定 | 現状維持 | 本体の再読込だけでなく、キャッシュのOwnerIDからusersを引くことでimage_locations/image_objectsの探索も省く。asia利用者の取得や海外キャッシュミスにも有効。海外ヒット時は内部204で本体の再転送を既に省いている |
| 初期画像の事前配布 | 別の改善候補として保留 | DB blobへのフォールバックを維持した任意の事前読込は可能。ただし初期化時間・一括転送量・256MiBキャッシュの追い出し・初期化世代との整合を実測する必要がある |
| 投稿フィールドのedge事前拒否 | 保留。認証後の判定順を維持 | 認証・リージョン・投稿条件・abuse記録より先に拒否すると既存の結果や記録が変わり得る。画像は有効なJPEGの検証証明のみを付け、不正な要求は従来処理へ通す |
| 海外SSEのDB直結を明示 | 対応済み | 上記のSSE節と説明HTMLに、認証・世代・バッチ確認・LISTENの直結経路と目的を追記 |

期限の検証は `getImageHandler` の画像SQLより前と応答直前にあり、`IPBanMiddleware` はその前に実行されます。単純にedgeで期限切れを拒否すると、IP制限対象への `ip_banned` が `image_forbidden` に変わる場合があります。期限の形式や検証結果を変えない条件（Clarification #39）も維持します。

保存LTSVのJob #16824を補助的に照合すると、海外の画像GETはisu2が832件、isu3が776件、うち403は3件と6件でした。この9件のexpは、ログの応答終了時刻の秒未満の幅を考慮しても未来であり、保存範囲では期限切れの海外403を確認できませんでした。403の原因自体はLTSVから断定できません。この1走行から一般的な効果は断定せず、現在の正常経路を変える優先度は低いと判断します。

asiaキャッシュも認可結果は保持せず、現在の秘密鍵と画像の有効性を毎回DBで確認します。キャッシュ削除の採否は「二重に本体を持つから」だけでは決めず、キャッシュ命中率・メモリ・画像探索SQL・ディスク/DB読込を測って判断します。初期画像の事前配布と合わせ、今回の構成の計測後に比較する候補です。

Issue #67の補足にある「遅延の影響を受けない」という線引きは、処理ごとに検証が必要です。画像の有効性確認SQLは同期応答の中にあり、海外HTTP往復とDB処理時間は直列に加わります。海外往復が支配的でもDB時間がゼロになるわけではありません。SSEもバッチ確認の完了まで配信を待つため、DB遅延は通知到着に加わります。バッチ化が減らすのは主に確認回数で、遅延自体を消すものではありません。初期化のような管理処理も制限時間内に収める必要があります。

## 成功時だけ返すエッジ読み取り（既定無効）

`edge_reads.go` に2つの独立した起動時フラグを追加しました。coreのハンドラ・SQL、通知、coreAdmission、Memoriesは変更しません。

| フラグ | エッジで完結する対象 |
| --- | --- |
| `ISUREAL_EDGE_IMAGE_VERIFY=true` | 本体キャッシュにある `GET /api/images/:imageId` の成功応答 |
| `ISUREAL_EDGE_READS=true` | `GET /api/posting-window/current`、`GET /api/posts/me/current` の成功応答 |

いずれも値が正確に `true` の場合だけ有効です。未設定・`false` では従来のproxyです。画像本体のキャッシュミスも従来のproxyを通ります。

各fast pathは既存のSSE用DBプールで1文だけ実行します。pgxの `QueryExecModeExec` により初回のprepare/describe往復も避けます。IPはcoreと同じ `extractClientIP` を使い、SQL内で `ip_bans.banned_until > clock_timestamp()` を照合します。セッション・ban・可視性のキャッシュ、追加プール、トランザクション、永続データ・初期化処理の変更はありません。

画像はcoreのmetadataOnly相当の `imageMissQuery` を再利用し、`image_locations` のcreated_atでパーティションを絞ります。キャッシュのOwnerIDが空でも所有者をDBから取得します。所有者がactiveで、参照元の削除・置換状態、署名形式・HMAC・期限、キャッシュのメディア種別と所有者が一致する場合だけ本体を返します。画像GETの可視性は既存SQLと同じ署名付きURLの判定です。URL発行側の友達・ブロック等の判定は変更しません。

読み取り2本はactiveなセッションとユーザー、現在のリージョンとエッジのRegionの一致、本体を1文で取得します。署名URLとレスポンス構造体はcoreの関数・型を使い、JSON末尾の改行も保ちます。窓なしのposting-windowはcoreと同じ200を返し、現在の投稿がなければcoreへ転送します。CanPostの開始時刻判定は要件に合わせDBの `clock_timestamp()` を使います（coreはSQL終了後のアプリ時計）。異なる時計や開始境界では判定時点の差があり得るため、完全な同時刻比較を保証する変更ではありません。画像期限と署名URLの発行時計は既存のアプリ時計のままです。

SQLエラー、対応表なし、不正署名、期限切れ、退会、無効セッション、リージョン不一致、banなどはエッジでエラーを返さず、何も応答に書かず既存proxyへ戻します。不正署名のabuse記録もcoreが処理します。成功時は既存ActionLogMiddlewareが同じaction・status・ip・user_id・levelでエッジの標準出力に記録します。設定されたログレベルのフィルタも同じです。coreには成功要求が届かなくなるため、その成功ログの記録先はエッジへ移ります。フラグ有効時の対象GETは専用routeになるため、fallback時にもエッジ側の既存ログのactionがnullから対象のaction名に変わります。fallback時のcoreのログとabuse記録は維持します。

通常のcore 200とfast pathのヘッダ・本文を比較します。HTTP DateはそれぞれのHTTPサーバーが生成するので比較から除きます。fallbackで画像キャッシュを使う既存経路は、従来どおりcoreが内部204を記録し、proxyが外向け200へ戻してContent-Lengthを除去します。この場合だけ比較テストはContent-Lengthと内部ログの204を既存挙動として扱います。

反映は担当者がベンチ外にエッジの新バイナリを配置し、必要なフラグだけ有効にして再起動します。DBスキーマ・接続先・nginx・coreの設定変更は不要です。切り戻しは対象フラグを `false` または未設定にしてエッジを再起動します。この変更だけを戻す場合は旧バイナリでも同じ永続データを読めます。画像ファイル保存方式そのものを撤去する場合の注意は上記の切り戻し手順に従ってください。

DBプールの上限は各エッジ最大30・アイドル10のままで、SSEと共有します。新たな専用接続は作りませんが、成功要求ごとに海外DB往復を占有するので、実際の同時接続数・プール待ちは増える可能性があります。SQL後にfallbackした要求はエッジの1文に加えて従来のcore SQLも走ります。core CPU削減量、海外DB待ち、DB接続数とSSEへの影響、スコアは実機未計測です。

ローカルの `edge_reads_test.go` は使い捨てDBの独立スキーマとloopback HTTPを使い、成功・各fallbackのステータス／本文のバイト一致、ログ、フラグ無効、SQL回数、prepareゼロ、core到達の有無を検証します。再起動相当のキャッシュ破棄とHTTPサーバー再生成は確認しますが、この追加変更の実プロセス・OS再起動、実機の初期化60秒以内、ネットワーク遅延込みの性能は未検証です。本作業ではサーバー操作・デプロイ・ベンチを実行しません。
